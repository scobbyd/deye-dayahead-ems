# emhass-deye-backtest

Would a battery on a Deye hybrid inverter have paid for itself on your house,
last year, on your prices? This repo answers that with real optimisation, not
a spreadsheet: it runs [EMHASS](https://github.com/davidusb-geek/emhass)
(the Energy Management for Home Assistant linear-programme planner) as a
library over your own 15-minute meter data, one plan per day, and settles each
plan on the day that actually happened. The reference plant it was built on
is a Deye SUN-12K with a 48,2 kWh LiFePO4 pack in the Netherlands on
day-ahead prices; every plant number is a config value, so change them.

The same planner core also runs live inside Home Assistant as a shadow EMS
(it plans, scores itself against the day, and does not touch the inverter).
That side is in `ha/` and is optional.

## Before you run anything: the three things this repo does not carry

These were deliberately stripped from the published copy. Nothing here works
sensibly until you supply your own.

1. **Your site coordinates.** Latitude, longitude and altitude drive the PV
   potential model and the EMHASS solver clock. The shipped values in
   `plant.example.json` are placeholders in the middle of the Netherlands.
   Copy the file to `plant.json` and set `site` to your roof.

2. **Your Solcast rooftop site ids.** The forecast lanes (`F_sol`, `F_mix`)
   and the live planner read Solcast per rooftop site. The ids in
   `plant.example.json` are `xxxx-xxxx-xxxx-xxxx`. Put your own under
   `pv.solcast_sites`, or run only the lanes that do not need Solcast
   (`P0`, `P1`, `P2`, `F_da`, `F_om0`).

3. **Your data.** No meter data, no plan archive and no golden test pin ship
   with the repo; they are one household's private record. You bring a
   15-minute frame CSV (schema in `docs/frame-schema.md`, builder in
   `backtest/ha_lts.py` for Home Assistant long-term statistics) and, if you
   run the live side, your own `/config/emhass/` archive grows from day one.
   The golden test suite skips until you build your own pin
   (`tests/golden/build.py`).

The scrub also removed the supplier names, the private hostnames and the
author's name from comments. Every engineering number, date and gotcha
stayed.

## Quick start

Python 3.12. Install, copy the site file, run the example:

```bash
pip install -r requirements.txt
cp plant.example.json plant.json
python -m backtest.quickcheck --frame examples/frame_synthetic.csv --lanes P1,F_da --capacity 24.1,48.2 --out runs/example
```

The example frame is synthetic: 14 April days of a house with no battery,
generated by `examples/make_synthetic_frame.py`. The run solves six days for
two lanes and two pack sizes (24 solves, under a minute), prints one line per
settled day, a block summary per pack size, and then the yearly and monthly
tables. The yearly table of that run:

```
lane  kWh days       from         to cash batt EUR cash nobatt EUR gain EUR gain/day kWh cycled EUR/kWh cycles/day
F_da 24,1    6 2026-04-20 2026-04-25         43,34            9,42    33,92     5,65        179   0,190       1,10
  P1 24,1    6 2026-04-20 2026-04-25         44,24            9,42    34,82     5,80        183   0,191       1,11
F_da 48,2    6 2026-04-20 2026-04-25         58,95            9,42    49,53     8,26        316   0,157       1,01
  P1 48,2    6 2026-04-20 2026-04-25         60,04            9,42    50,62     8,44        322   0,157       1,03
```

`cash batt EUR` is what the house earned at the meter with the planned pack,
`cash nobatt EUR` the same house with no pack on the same day, `gain EUR` the
difference, `EUR/kWh` that gain per kWh discharged. Money is EUR in, European
decimals. The numbers mean nothing about any real house; the shape of the
tables is what the example shows.

To run it on your own house, build a frame CSV (one row per quarter hour,
UTC, the columns in `docs/frame-schema.md`): from Home Assistant long-term
statistics with `python -m backtest.ha_lts build --start ... --end ...`
(entity map at the top of `backtest/ha_lts.py`, `HA_URL` and `HA_LLAT` in
`.env`), or from any CSV export by renaming its columns onto the contract. A
house without a battery writes `batt_dc_w` 0 and `soc_pct` 50; the settlement
then adds the planned pack to your real day. Set `site` in `plant.json` to
your roof, then run the same command with `--frame data/frame.csv`; without
`--capacity` it uses the pack in `plant.json`, and `--start`/`--end` narrow
the range (the default skips the first week and the last horizon day).

`--capacity 16,32,48.2 [--inverter 12]` is the sweep: one ladder run per pack
size, one CSV each under `--out`, resumable; read the yearly table across
sizes for where the marginal kWh stops paying.

## What the numbers mean

The harness runs a **knowledge ladder**: the same day is planned several
times, each lane knowing a different amount, and every lane is settled on the
measured day with the same accounting. The gap between lanes is the value of
what each one knew.

| Lane | Knows | Use it for |
|---|---|---|
| `P0` | the coming day exactly (PV, load, prices) | upper bound, 1-day horizon |
| `P1` | two days exactly | the usual "perfect foresight" reference |
| `P2` | three days exactly | horizon sensitivity |
| `F_da` | real prices, Open-Meteo PV issued the day before, 7-day load profile | what a live controller would have done |
| `F_sol` | as `F_da` but Solcast PV | needs your Solcast ids |
| `F_mix` | Solcast P50/P10 blend | the live planner's default PV |
| `F_om0` | Open-Meteo PV issued the same day | forecast-lead sensitivity |

For each day and lane you get the cash with the battery, the same house with
no battery (`nobatt`), the battery gain, the energy through the pack and the
gain per kWh cycled. The yearly table sums those. A `--capacity` sweep runs
the ladder for several pack sizes so you can read where the marginal kWh
stops paying.

Settlement includes what a spreadsheet leaves out: the 12 kW DC-AC bridge cap,
the quadratic stage losses of the Deye (port and bridge, priced at the slot's
price), PV curtailment when the pack is full and export is off, and the SOC
band you allow. Read `docs/method.md` for the accounting and the gotchas.

## Layout

```
plant.example.json   every site number: coordinates, pack, inverter, grid cap, PV strings, Solcast ids, tariff
emhasscore/          the planner core (standard library only; also runs inside pyscript in HA)
backtest/            the offline harness: frame schema, HA statistics puller, ladder, solver, quickcheck, replay
tests/               pytest; the golden pin is built from your own archive
ha/                  the live shadow EMS: HA package, pyscript wrapper, add-on config, deploy scripts
docs/                frame schema, method, lanes
examples/            a synthetic 14-day frame so the quick start runs on a clean clone
```

## Requirements

Python 3.12, `pip install -r requirements.txt`. EMHASS 0.18.2 is pinned; the
solver contract (`build_config`, `build_params`, `set_input_data_dict`,
`naive_mpc_optim`) is what `backtest/solver.py` wraps. pvlib is only needed
for the PV potential model, plotly only for the viewers.

## Not included

- The dashboard tab. It depends on a private theme and card stack. The
  sensors to chart are listed in `ha/README.md`.
- The household frame builder that merged a supplier's quarter-hour export,
  CAMS irradiance and KNMI weather. The public path is HA long-term
  statistics.
- Any measured data.
